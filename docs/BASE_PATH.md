# Base path — деплой под префиксом

Релей может жить не только в корне хоста, но и под путём:
`https://<host>/<slug>/...`. Это позволяет ставить релей на домен, занятый
другим сайтом (nginx отдаёт чужой сайт в корне, релей — под префиксом).

## Слаг

- Задаётся `TPROXY_BASE_PATH` (конфиг `base_path`).
- По умолчанию (`deploy/production/setup.sh`) генерируется автоматически:
  **RFC 4648 base32 нижнего регистра от 10 случайных байт** — ровно 16
  символов без паддинга (10 байт = две группы по 5, паддинг не нужен).
- Формат: сегменты `[A-Za-z0-9][A-Za-z0-9_-]*`, разделённые `/`, до 128
  символов — проверяется при старте (иначе отказ запуска).

## Что меняется при включении

1. Все транспортные пути переезжают под `/<base>/`:
   `/<base>/api/v1/session|up|down|ws`; корень `/<base>/` — точка входа моста.
   Только форма со слэшем на конце; `/<base>` без слэша — обычный 404.
2. **Capability меняет контекст вывода** (см. [PROTOCOL.md](PROTOCOL.md)):
   `v2\n<hostname>\n<path>` — старые ссылки на креды перестают работать,
   клиенты должны переподключиться по новой ссылке.
3. Страница моста получает `var BASE='/<base>/'` и строит все запросы
   относительно префикса.

## Маркированный секрет и ссылки t.me

При включённом base path секрет в ссылках для клиентов меняет форму:
`base64url(0x70 || secret)` — **маркированный** секрет с префиксом 0x70,
17 байт. Символ `/` внутри base64url не встречается, поэтому ссылка
кодируется с `%2F` для t.me (`ProxyLinks.Tme`). Клиент Telegram понимает обе
формы секрета; маркированная сообщает ему, что прокси живёт под путём.

## Эксплуатация

- Включение/смена base path — это смена кредов для всех клиентов: сначала
  включите, потом выдайте новые ссылки (Admin API `/admin/keys` и `/key` бота
  учитывают base path автоматически).
- Откат на корень — та же процедура в обратную сторону.
- nginx (Mode A): достаточно проксировать всё на релей — префикс обрабатывается
  внутри; ничего в nginx менять не нужно.
